# 银河证券成交 CSV 导入设计

## 状态

已确认的实现设计；本文件不包含功能实现。

## 目标

支持将银河证券客户端导出的成交 CSV 导入本地 SQLite 账本，以便在盘后复盘中查看实际发生的买卖成交。导入数据是用户提供的券商导出文件内容，不代表本系统已向券商核验，也不构成账户实时状态。

首版支持样例 `563360.csv` 对应的导出格式、任意有效六位证券代码和多交易日文件；只接受买入、卖出成交。首版假设一个账本对应一个银河证券账户。

## 非目标

- 不连接券商，不验证文件数据是否与券商当前记录一致。
- 不由成交记录自动推导或更新持仓、可卖数量、现金、账户快照或底仓。
- 不导入申购、赎回等非买卖操作；不支持其他券商或其他 CSV 方言。
- 不保存股东账户号、资金余额或整行原始 CSV。
- 不把导入成交合并为手工录入成交，也不把其分类标成券商实时核实。

## 输入格式

样例列顺序如下，末尾还带有一个无列名的空字段：

| 样例列                                     | 导入用途                                                 |
| ------------------------------------------ | -------------------------------------------------------- |
| 成交日期、成交时间                         | 合并为成交时间，按 `Asia/Shanghai` 解释                  |
| 证券代码                                   | 标准化为项目使用的六位代码                               |
| 证券名称                                   | 不作为证券身份或估值依据                                 |
| 操作                                       | 仅映射“买入”→ `buy`、“卖出”→ `sell`                      |
| 成交数量                                   | 正整数                                                   |
| 成交均价                                   | 正十进制数，映射为成交价格                               |
| 成交金额                                   | 正十进制数，保留用于核对                                 |
| 合同编号、成交编号                         | 来源记录标识；成交编号用于幂等导入                       |
| 手续费、印花税、其他杂费                   | 非负十进制数，保留用于核对                               |
| 发生金额                                   | 有符号十进制数，保留券商原值用于核对，不用于更新账户现金 |
| 资金余额                                   | 不读取持久化                                             |
| 交易市场、股东帐户、交收日期、证券中文全称 | 不持久化；市场字段不参与推导证券代码或市场状态           |
| 末尾空字段                                 | 允许且忽略；其他不符合样例的表头/结构拒绝                |

样例通过 GB18030 解码后可正确读取中文字段。首版读取该编码，不做编码猜测或静默替换字符。解析必须识别完整预期表头；除样例末尾的空字段外，列缺失、重复或结构不匹配均作为文件级格式错误。空白行可忽略。

## 入口与用户流程

增加 CLI 子命令，建议形式：

```text
python -m a500_t_trader import-fills --file fills.csv --database account.sqlite
python -m a500_t_trader import-fills --file fills.csv --database account.sqlite --confirm
```

不带 `--confirm` 时只解析、校验、查重并输出预览结果，不写数据库；带 `--confirm` 时执行同样的校验，并仅在文件无错误后写入。预览与确认阶段应分别报告有效记录数、新增数、已存在重复数和错误数；错误包含 CSV 行号及具体字段/原因。存在任何解析、校验或标识冲突错误时，退出失败且不写入任何行。成功写入时输出新增数及导入记录 ID（或等价的明确成功结果）。

提供可复用的账本导入 API；CLI 不自行实现 CSV 映射或 SQL 写入。

### REST API 扩展

在现有认证账户 API 中提供成交文件导入 REST API。请求使用 `multipart/form-data` 上传文件；用户身份只取自已验证 OIDC Bearer JWT 的 `sub`，不接受客户端提供的用户或账本标识。仅允许现有银河证券 CSV 格式。

API 保留显式预览与确认两阶段：

- 预览阶段解析、校验并查重，不写成交记录；返回批次 ID 和有效、新增、重复、错误计数及脱敏错误详情。
- 预览记录暂存 15 分钟；只暂存解析后的记录，不保存原始 CSV。过期批次不可确认。
- 确认请求引用批次 ID；确认成功后保留可查询的确认结果，但不得再次写入。确认失败可在过期前重试。
- 确认时对该批次执行同等校验，并在单个事务中写入；任一文件/行错误或标识冲突均不得部分写入。
- 同步处理预览与确认。上传文件上限为 5 MiB，记录数上限为 10,000；超限请求明确拒绝。

导入成交存于共享数据库，并按已验证的用户 `sub` 隔离；重复成交编号仅在同一用户范围内去重。导入不更新账户现金、持仓、可卖数量、保护底仓或账户快照。错误和响应不得泄露股东账户号、资金余额或原始 CSV 行。

## 存储与数据映射

在现有 `manual_fills` 之外增加独立的券商文件导入成交存储。记录至少包括：

- 成交时间、标准化证券代码、方向、数量、成交均价；
- 成交金额、手续费、印花税、其他杂费、发生金额；
- 导入来源标识及成交编号、合同编号；
- 现有账本记录所需的分类/来源说明，明确标记为银河证券文件导入且未经系统核实。

不保存股东账户号、资金余额、整行原文或 CSV 的其他未列入持久化映射的字段。金额、费用及价格以十进制文本或等价无损表示存储，不经二进制浮点数转换。交易数量必须是正整数；价格和成交金额必须为有限正数；费用必须为有限非负数；发生金额必须为有限数。成交日期时间必须有效，方向必须能映射到买/卖，证券代码必须通过项目现有证券代码标准化规则。

## 去重、冲突与事务

导入来源固定为该银河 CSV 方言；在单账户前提下，以“来源标识 + 成交编号”作为唯一去重键。

- 已存在且成交关键内容一致的成交：计为重复，不再插入；重复项不构成整批失败。
- 同一文件内或数据库中出现同一去重键、但证券、方向、时间、数量或价格等成交核心内容不一致：报告冲突并拒绝整批，不静默选取其中一条。
- 成交编号缺失或为空：作为行错误；不退化为按时间/价格猜测去重。
- 校验无错误后，在单个 SQLite 事务中写入本批所有新记录。写入过程中任何失败均回滚本批新增记录。

成交编号只在同一来源账户的假设下作为稳定标识。若将来需要在同一账本导入多个账户，必须先重新设计账户隔离和去重键，不能继续假设成交编号全局唯一。

## 盘后复盘与账本读取

盘后复盘应读取独立存储的导入成交，并与 `manual_fills` 分别呈现，包含清晰的来源/分类区分；不可将两种来源合并成无法区分的手工成交列表。按成交时间排序。现有手工录入和账户快照行为保持不变。

账本查询输出应能区分手工成交与导入成交，并带出导入成交的费用、成交金额和来源标识供对账。该展示仅为文件数据复核，不代表账户现金或持仓计算结果。

## 失败行为与隐私

文件级错误（编码、表头、结构）应在写入前报告并拒绝整个文件。行级错误报告原始 CSV 行号；一次导入中只要有一行错误，整批均不写入。错误消息不得输出股东账户号或整行 CSV 内容。预览也只显示必要的汇总和脱敏后的错误定位，不打印敏感字段。

## 验收标准

1. 样例文件可识别中文表头，末尾空列可接受；样例买入/卖出记录映射为正确的时间、证券、数量、价格和费用字段。
2. 多交易日及多个有效证券代码可在一个文件中导入；买卖以外的操作、非法时间/数值/数量/代码和缺失成交编号均明确报错。
3. 默认预览不写数据库；只有提供 `--confirm` 才写入。任意行错误或标识冲突均导致整批零写入。
4. 同一有效文件重复导入不会重复插入；相同成交编号对应不一致核心成交内容时拒绝导入。
5. 导入成交与手工成交在存储、账本查询和盘后复盘中保持可区分；复盘不将成交转化为现金或持仓更新。
6. 持久化结果中没有股东账户号、资金余额或 CSV 原始整行；费用与金额使用无损十进制表达。
