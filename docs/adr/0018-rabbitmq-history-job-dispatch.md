# 历史日线查询任务通过 RabbitMQ 派发

状态：已决定，尚未实现。

历史日线查询任务目前由 API 写入 PostgreSQL，worker 轮询数据库领取。为后续拆分独立服务，任务派发改用 RabbitMQ；本次保留共享 PostgreSQL 中的任务状态、取消请求、分片进度和结果，不将数据库所有权拆分纳入范围。worker 必须能作为独立部署单元运行，但共享数据库意味着 API 和 worker 尚未完全解耦。

## 决策

- 提交任务时，在同一 PostgreSQL 事务中保存任务和待发布的 outbox 记录；由后台发布进程向 RabbitMQ 派发，失败时重试。HTTP `202` 表示任务已可靠保存，不表示消息已送达或 worker 已开始执行。RabbitMQ 不可用时仍接受提交，任务保持 `queued`，恢复后继续派发；部署者需监控积压。
- 为历史任务使用独立的 exchange 和 durable queue，不复用行情队列；共用现有 RabbitMQ 实例，因此仍共享 broker 故障域。消息允许重复投递，不承诺 exactly-once。worker 必须结合数据库状态和租约幂等领取与处理，不能因重复消息破坏进度或结果。
- 保留现有租约、心跳、取消、分片检查点及中断恢复语义。worker 崩溃后，即使消息已重投而旧租约尚未到期，也必须在租约到期后最终恢复未完成任务，从已完成分片继续；不能只依赖一次消息重投。成功任务的结果保持固定。
- 保持现有外部提交、状态查询、取消和结果接口，以及认证主体隔离和任务行为不变。状态与结果继续从 PostgreSQL 查询，不通过 MQ 返回给客户端。
- 升级时先停止旧的数据库轮询 worker，再启动新版本；期间允许继续提交并排队。新版本自动为存量未完成任务补派发或接管，运行中的任务按租约到期规则恢复，避免新旧 worker 并行争抢。

## 取舍

事务性 outbox 避免数据库提交成功但消息发布失败时任务永久丢失，代价是增加发布和积压运维。相较于让 API 与 worker 的全部状态和结果交互都经过 MQ，本方案只解耦任务派发和部署；独立数据所有权、跨服务查询和完全隔离的 broker 留待未来单独决策。
