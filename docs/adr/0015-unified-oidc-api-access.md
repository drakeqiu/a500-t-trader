# Protect web access and public APIs with OIDC

The account API already validates OIDC bearer JWTs, while the signal API and web frontend have no application-level authentication. Protect the web application and all public business API routes with one trusted OIDC issuer and a dedicated audience shared by the APIs; each API validates the JWT signature, issuer, audience, and validity rather than relying only on a reverse proxy. This supersedes ADR 0011's statement that application authentication is out of scope; its signal-computation and transport decisions remain unchanged. The identity provider controls which users are allowed to sign in, with no application self-registration. The browser uses Authorization Code with PKCE and keeps access tokens in memory. Authenticated users share market data and signals; account snapshots and imported trades remain scoped to the verified `sub`. `/healthz` is internal-only, while API documentation and OpenAPI schema require authentication. The existing account API audience (`a500-account-api`) must be migrated with the identity-provider and service configuration to the shared audience. A shared audience simplifies browser access across APIs but means a token for that audience is accepted by each participating API.
