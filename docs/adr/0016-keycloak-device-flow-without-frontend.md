# Use Keycloak device authorization; retain it for the approved frontend

**Historical status:** The Keycloak provider choice and setup below are superseded by the Rauthy cutover in #232. The historical OAuth flow and API-boundary rationale remain for context; this document is not an active runtime configuration.

The browser client and its Authorization Code with PKCE flow from ADR-0015 were superseded by the original decision to provide no bundled browser frontend, CLI, or SDK; callers obtained tokens directly from the trusted OIDC provider using OAuth 2.0 Device Authorization Flow. Keycloak remains the Compose-managed provider for local and test environments, with its data persisted in a named volume; production may use an externally managed Keycloak instance. A reproducible realm configuration enables a public client for device authorization and issues access tokens for the shared `a500-api` audience, without committing client secrets or default users. Administrators provision permitted users in Keycloak; self-registration remains disabled. A500 APIs only validate IdP-issued Bearer access tokens and identify account ownership by verified `sub`; they do not expose login routes, validate passwords, issue tokens, or refresh them. Token lifetime and refresh policy belong to Keycloak, and callers are responsible for safely storing and refreshing tokens.

## 2026-11-06: user-approved local frontend integration

The user explicitly approved the existing Next.js browser workspace and its real local integration, superseding only the no-frontend portion above. This does not reinstate Authorization Code with PKCE: the browser remains a public device-authorization client, stores access tokens only in page memory, does not automatically use refresh tokens, and requires device reauthorization after reload, expiry, or invalidation. Password entry remains at Keycloak, never at A500.

The local launcher combines the Python services, gateway, Keycloak, RabbitMQ/Redis and frontend. Next.js rewrites same-origin `/api/v1/*` to the existing gateway `/v1/*`; it adds no business backend or token broker. The local public issuer is `http://localhost:8081/realms/a500`, while API containers fetch JWKS over `http://keycloak:8080/realms/a500/protocol/openid-connect/certs`. The realm's device client allows only the local frontend origin `http://localhost:3000`; changing an existing realm requires an explicit administrator update because realm import is not reapplied to persisted data. Backend CLI and direct Bearer API access remain supported.

The approved browser scope is current signals, user-entered account snapshot editing with ETag conflicts retaining drafts, truthful NAV availability, and CSV preview/confirmation with same-subject batch recovery. Imports do not update snapshots. Deployment management, orders and account history are not added.

## 2026-11-07: browser authorization code

The user chose OIDC Authorization Code with PKCE S256 for the browser instead of device authorization. The public browser client uses exact redirect URIs and origins, keeps access tokens only in page memory, and does not persist refresh tokens. Reload or expiry requires another authorization redirect; an existing Keycloak session can avoid another password prompt. Passwords remain with the IdP and API authentication and per-subject ownership are unchanged. The separate device client remains available to direct API callers.
